     chain (`conversation_checkpoints_carry`) and main forgets the conversation

     `STRATA_SLOT_CKPT_MOVE` / deepest-checkpoint logic runs as before.

     chain instead of duplicating it.
5. `serve/server.py`: `TURN_ID` (upstream's #2518 turn-boundary rule) and `SLOT_REWRITE_MIN`
   (the fork's shared-majority rule) both stay. The rule is upstream's first and the fork's as
   the fallback: a prompt that agrees with the slot's held tokens up to the last `<|im_start|>`

   rewritten tail is as well - neither branch loses the behaviour the other had.
6. `docs/DETAILS.md`: the WSL `cudaHostRegister` paragraph and the `--kv-pool-tokens` section
   are both additive - kept.

### How big does the shared KV pool have to be? (the "1 or 2 lanes" question)

`--kv-pool-tokens N` (the C# side's `kv_pool_cells`, ABI v23) pins **N cells per streamed QSA
layer, shared by every lane** (main session + batch slots, and across the stages of a layer
split). A lane reserves `ceil(cells / 4096)` chunks as its conversation grows, so what has to
fit is the **sum** of the lanes' reached cells - the split between them is free (200k + 50k is
as fine as 130k + 130k). Per-lane context stays `--max-context`; the pool is the aggregate
ceiling. When it runs out: an idle slot's cached conversation gives way first (`KV pool full:
slot N gives back its cached conversation`), then the request is refused (HTTP 503
`kv_pool_full`) or a decoding lane ends `length` with `"truncated": true`.

Measured cost (fp16, the prod format, from the pool line): **3.09 GiB per 131,072 cells** over
two stages.

| pool | pinned (fp16) | allows |
|---|---|---|
| 262,144 (64 chunks) | ~6.2 GiB - what ONE fp16 lane already costs today | one conversation at 255k, **or** any two lanes summing to <=255k |
| 393,216 | ~9.3 GiB | sum <=384k (e.g. 200k + 190k) |
| 524,288 | ~12.4 GiB | two full 255k conversations |

The box has 58 GB RAM (11-16 GB available with the host up). Today's prod/host config spends
`--conversation-cache-mib 12288` on the RAM parking budget, but **that budget is not pinned and
PLA's id-carrying conversations take the disk path** (`--conversation-disk-dir`,
`--conversation-disk-gib 96`, 114 GB free; the box's conversations dir was empty and the live
log showed 0 parks). So cutting that budget to ~4 GiB funds the 524,288-cell pool without a RAM
regression; the 262,144-cell pool is RAM-neutral (it replaces the single lane's own pinning).

### The three routes, and what "two requests in parallel" costs on this box

The C# app has two engine routes, selected by env:

| route | who does the work | how it is selected | parallel 2 |
|---|---|---|---|
| kernel path (what prod/live runs) | the kernel (`strata --serve`) as a subprocess over `libengine_shim.so` | `STRATA_LIBRARY_PATH` + `STRATA_ENGINE_BIN` (default) | the kernel's `--batch N` (+ 0.1.45's `--batch-groups`) |
| own engine (the P15 line) | the C# `OwnEngine` over `libsexec.so` in process (the same ABI the `sexec-box-step` probe uses) | `STRATASHARP_ENGINE=own` + `--own-*`/`STRATASHARP_OWN_*` | `--own-seq-slots N` + `--own-kv-pool-cells M` (the lanes on the shared pool, ABI v23) |
| (both are the same strata engine code, different entry surface) | | | |

Measured on the box (2026-10-18):

- **Kernel path, `--batch 2`**: the 0.1.45 kernel accepts the flags and prints `--batch-groups auto: 2
  groups of 1 slot` (and "`--pipeline-windows 2 is off: not with --batch slots`"), but on this box it
  then **answers `batch_slots=0`** - the host logs "solo service mode (ADR-0007): this kernel answers
  batch_slots=0 - no batch slot exists on it" and serves every turn on the kernel's GEN path. Without
  the resident headroom the *load* dies instead (`shim: the kernel exited before READY`, three retries,
  `MEM avail=4.7 GB` during the 32.98 GiB page-locked complement); with
  `STRATA_RESIDENT_HEADROOM_GIB=16` it loads and trims to solo (turns then answer: 57-61 tok/s
  generated, 51-68 of 78-101 drafts accepted, 97 % cache hit, warm file tier). So: **the kernel route
  cannot do parallel 2 on this box** - the RAM (58 GiB LXC) is the wall, and the kernel declines
  gracefully rather than dying.
- **Own engine, the lanes** (probe = the same ABI): two lanes on the pool read an 8192-id prompt in
  **7.65 s against 15.5 s solo (2.03x)** at 65k, and at **255k** in 7.73/7.76 s against 16.2-17.6 s
  (2.1-2.3x), with `SLOTS-AB: VERDICT A: identical id for id` and 0 refusals. Decode: 2 ids per
  40.1-41.0 ms step against 28.2-29.4 ms/window for one (~1.4x).
- **The lanes at 255k need the CUDA1 expert cache at ~4000 slots** (7.92 GiB): the load's capacity at
  that context is 4356 slots (a request of 4360 is refused: "the pinned cache of 4360 slots does not
  fit: room 8.63 GiB ... holds 4356 profile pairs"), and at 4300 the *decode window* OOMs
  ("verify: instantiate: out of memory") while 4000 and 3700 decode fine - the 4000 vs 3700 difference
  in the measured times is 0.4 % (noise). The live host's CUDA1 cache is 4342 slots.
- **The drafter** can only leave the last stage when the pipelined windows are on and the draft head is
  the subset file (`sexec/drafter_card.h`: "Moving the drafter OFF the last card requires serve's
  eligibility (mtp_first_ok: the subset draft head, the pipeline, a layer split)"), and the sexec path
  *refuses* lanes + `pipeline_depth >= 2` (`fork_load.cpp`: "the slot lanes run serial windows"). So in
  the lanes shape its 1.39 GiB (863 + 215 + 311 MiB) stays on CUDA1.

## Residual correctness risk after dev gates

The semantic class, as in PORT-01441: our park_view/protect/disk-parking x upstream's
borrow/guarded-donor/park-gain under the prompt path `fork_load.cpp` re-expresses; the batch
slot paths where the pool's chunk move meets upstream's device-to-device slot copy

reads). The AB probe, the p9b identity window, the parity x3 and the pool-on checks above are
exactly the gates that see that class. Upstream's release gates covered their own code.

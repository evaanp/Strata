## The `parallel` question (upstream #465)

**Verdict: keep `"parallel"` out of the prod config for now; measure on the box before enabling.**
Everything below is read from this tree (the released 0.1.39 plus our port), so the pre-release caveats in
`~/strata-batch/ANALYSIS-batch-559.md` are re-checked against shipped code, not the fetched `bd400f7`.

**How it is switched on.** `"parallel": N` in the arena config maps to `--batch N`
(`serve/server.py:1495-1513`); `PARALLEL_MAX = 8` (`serve/server.py:1492`) is the engine's window cap
`kVerifyMaxT = 8` (`include/strata/kernels/verify_kernels.hpp:21`). The server reads the engine's real slot
count back and says when it is lower than asked (`serve/server.py:488-493`); the web monitor gets
`parallel`/`slots`/`outside_slots` (`serve/server.py:2139`). Nothing changes without the key.

**What it costs on our cards.** Each batch slot gets its own full `session_bytes(g, max_context, K, lo, hi)`
session **per stage card**, cudaMalloc'd at start (`src/program/generate.cpp:3288-3316`); if two do not fit,
`--batch` turns itself off with a warning (`:3319-3324`), and the engine prints that the slot sessions take
VRAM the expert cache would otherwise hold (`:3328-3330`). `session_bytes` scales with `max_cells`
(`src/core/session.cpp:54-73`), so at our `--max-context 153600` the per-slot price is the same structure as
the ANALYSIS §5 table (≈0.5 GiB CUDA0 + ≈0.37 GiB CUDA1 VRAM, ≈1.5 GiB pinned RAM per slot - those figures
are from the pre-release analysis and must be re-measured). The trim runs in prod only once
`--trim-stage-weights` is in the engine args (see "Fewer experts in VRAM" below - without it, 0.1.39-pla1
loads full dense copies on every card, unlike our old default-on carve); with it on there is no trim
headroom to bank: the slots come
straight out of expert-cache residency, which ANALYSIS measured as the dominant batch throughput risk
(205 -> 105 tok/s at 4 slots on their control run).

**What the release fixed since that analysis.**
- *Slot output is now parked.* `copy_from_slot` (`generate.cpp:6541-6560`) copies a finished slot's sessions
  back stage by stage, and the handler parks the outgoing conversation before any handover
  (`park_current`, `:7114`); an idle slot marks its state cached at BDONE (`:6626-6628`), and the RAM
  conversation cache wins over a slot-held copy when both match (`:7087`). The per-turn re-prefill gap is gone.
- *Our disk key rides the batch protocol.* `sampling_keys()` appends `conv=ID` on **both** GEN and BGEN heads
  (`serve/server.py:699`, used at `:884` and `:974`); the engine parses it in the shared read path
  (`generate.cpp:6850`).
- *Pipelining is legal on our two-card split*: `--batch-groups G` needs a layer split and G dividing N
  (`generate.cpp:3283-3286`; re-checked after any auto-shrink at `:3326`); piped windows run
  `GS = batch / groups` rows per stage (`:6658-6659`).

**What the release did NOT fix.**
- *Penalties are still hard-zeroed in batch windows*: `Verifier::sample_rows` copies each slot's
  `SamplerParams`, then `sp.penalty_last_n = 0;` and passes `nullptr` history (`src/core/verify.cpp:2050-2063`).
  Prod runs `presence_penalty 1.0` (thinking loops without it, measured on the box) - every batched turn would
  lose it. The ANALYSIS §4 patch (~100-150 lines: per-slot history ring -> existing `penalty_rows` ->
  existing `d_hist`) is still required before PLA uses batch.
- *No MTP drafts in slots*: `--batch-spec` does not exist anywhere in 0.1.39 (`grep -rn 'batch-spec' src serve
  tools` empty). The server's policy stands: a solo request keeps drafts; when a second arrives it is STOPped
  and re-admitted via `BGEN` with prompt + generated so far, prefix-exact through the prompt cache
  (`serve/server.py:874-1034`). Two concurrent PLA streams therefore decode at draftless window rate.

**Decision.** On two 16 GB cards with the split, `--batch 2` buys wall-clock concurrency (both conversations
advance between tool calls) at roughly today's aggregate rate, and risks expert-cache hit rate (+~1 GiB
VRAM/card) plus the penalty gap. Not worth shipping unmeasured: keep `"parallel"` absent, run the measurements
below on the box, and gate enabling on them. If penalties prove to matter (they will for PLA), land the ring
patch first; upstream is the right home for it - note it when #465 discussion continues.

## Fewer experts in VRAM: #639 vs the dropped carve

0.1.38-pla1-prefix ran CUDA0 5696 slots, CUDA1 5795, 11491 resident; 0.1.39-pla1 with the same config:
5005 / 4653 / 9658 (-16%). The cause is in the code, and it is the whole story. Our layer carve
(f05298c/74f29e7/ecce4fe/71aba72) was dropped for #639, but #639's loader trim is **opt-in on both
backends**: `generate.cpp:2378` gates it on `--trim-stage-weights` or `STRATA_STAGE_TRIM`, and the prod
config passes neither. Without it every stage cudaMalloc's the whole model's dense arena again
(`skip_s = skip`, `:2813`), and `--expert-cache auto` sizes from what is left.

What each stage loads, read out of the code: with the trim on, CUDA0 skips every `blk.*` outside its range
and carves the native projections with `set_layer_range(0, 30)` (`:2401-2405`); each later stage does the
same for its own range (`:2801-2810`). PLE tensors stay everywhere; CUDA0 keeps every router only with
`--mmap-experts`. That is exactly our carve, CUDA0's own layers included - 71aba72 is covered. The loss's
fingerprint matches: the slot deltas 691/1142 = 0.61 sit on the foreign-layer ratio 18/30 of a 48-layer
model split at 30 (DETAILS.md: 48 layers) - dense copies, not any other change.

**Production needs `--trim-stage-weights` in the engine args** (`layer_split: 30` is explicit, so the
switch applies). Expected recovery: the full -16%, back to ~5696/~5795. The GB figure belongs to the box:
the load-time lines `layer split: CUDA%d loads the dense weights of layers ... only` print the per-card
dense MiB in both arms; measure there, not here (no GPU, no pack on this machine).

Where #639 leaves our carve's savings on the table: `--layer-split auto`. Our old `weight_slice` trimmed
under an auto search too; #639 refuses (`!split_auto` at `:2378`; `--trim-stage-weights` warns "needs an
explicit --layer-split"). Prod pins 30, so nothing is lost today - if we ever move to `auto`, each card
again holds the other stages' dense weights (18/30 of them at this split). Related upstream inconsistency
to report: the placement search prices with our carve model by default (`weight_bytes`/`cuda0_bytes`,
`STRATA_WEIGHT_SLICE` default on, `:2729-2737`) while the loader trims only with the switch - an `auto`
search prices bytes it will never load. Prod's explicit split does not search, so this costs nothing today.

## Disk parking never restored under a layer split (regression, round 2)

`strata:0.1.39-pla2` (b63ea54) with `layer_split 30`: every park wrote its files, every restore was thrown away -
`discard a (conversation disk: the running state does not match the stage set)` - so each switch back was a full
re-prefill (an 84K-token conversation came back with `0 reused`). The parity tool's `disk` scenario failed with
`A+ state differs from the baseline`; `reuse` (RAM) stayed byte-exact.

Cause: merge f504c2c brought over 0.1.39's load side, which requires a split conversation's per-stage running
states (`SavedConversation::stage_images`), but `conversation_disk.cpp` still wrote the 0.1.38 layout - one live
record for stage 0 only, `stage_images` never serialized to disk. The unit tests missed it because no test parked
a two-stage conversation through `ConversationDisk`; the cache-level tests exercise RAM images and the snapshot
tests never call `park`.

Fix (7cd0930): `live.bin` gets a format word, then stage 0's record followed by one record per later stage, all
rewritten on every park; `load` reads them back into `stage_images` and matches every stage's ids/images against
the index. An entry without the format word - written by an older binary - is refused by name ("older strata") so
the caller drops it and re-prefills, instead of restoring a half-understood image. The load-side K/V extent check
already iterated `conversation_kv_entries` (every stage plus the drafter on the last stage); the test now asserts
the restore moves exactly that many bytes.

Now covered by: the disk round-trip block in `split_fixture` (`src/core/conversation_validation_test.cpp`,
transfer build): park -> load -> `restore` into both stages -> re-park (keeps the K/V, writes less) -> strip the
format word and watch the entry get refused and dropped. It was RED at a2ad0f2 with exactly the production
message; the transfer build now runs 1668 checks (was 1599). The test also pins one engine behavior I first
expected wrongly: `live_restore` re-folds each stage's spare pooled indexer row from its parked `dead` payload
(upstream design, `conversation_state.cpp:185-188`), so that row is not expected to come back byte-identical to
what the pool held before parking.

What else I checked where the merge touched the split model:
- Keyless prefix entries: under a split, generate.cpp saves one `conversation_prefix_save` part per stage into
  `stage_images` (5768-5788) - same shape as a full park. They live in RAM only: `ConversationDisk::park` always
  captures from the live session, so a prefix entry can never reach disk with a stale layout.
- Mid-prompt checkpoints: the disk format round-trips the merged chain including each checkpoint's `stage_parts`
  (the new test asserts one through park/load); the RAM path keeps them split per stage in
  `stage_images[i].checkpoints` and generate re-merges them with `conversation_checkpoints_merge` (7299-7301).
  Both forms carry every stage's payload; neither can lose a part under a split anymore.
- `conversation_transfer`: no such code exists in 0.1.39 - the name is only this repo's test target. Nothing to
